# Data Agent V3：运行中补充与同 Run 续答

2026-11-26 · 待评审 · 基线：V3 `0e66277`、Datus-agent `59bb0a3`

## 目标与范围

用户看到 Agent 正在查数或已经开始回答时，仍可点击「补充本轮」。正在执行的请求和已经发出的内容都不撤回。收到的补充在下一个**业务模型请求**前进入同一个 Run；会话 ID、Run ID 和 `turnNo` 不变。

例如：用户问「现在 UTC 几点？」；Agent 开始逐字回答「UTC 02:00」。此时用户补充「也给我北京时间」。已有回答继续显示，结束后对话依次呈现「UTC 02:00 → 也给我北京时间 → 北京时间 10:00」。续答使用已有时刻做时区换算，无需重查当前时间。这个行为应通过可控模型验证，不承诺任意模型都能正确理解补充。

本期仅处理单实例 V3 的文字补充。**不做**：取消或改写已经发出的模型请求、回滚已执行工具、自动创建下一 Run、重启续跑、重新设计会话历史分页、引入供应商专有的 steering API。已有 8 次业务模型请求上限不变；入口在第 8 次请求取件时关闭，不在第一段文字时关闭。

## 参考 Datus 的取舍

[Datus 接收入口](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/api/routes/chat_routes.py#L556-L611) 将输入放入任务队列；[模型请求边界](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/models/claude_model.py#L914-L951) 在工具结果完整之后、压缩之前按 FIFO 注入独立的 `user` 消息；[尾部续接](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/api/services/chat_task_manager.py#L1307-L1365) 在当前执行结束后用剩余文本开启新轮次；[压缩视图](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/agent/node/context_rewriter.py#L218-L272) 保留本轮真实用户输入。

| 方案 | 判断 |
| --- | --- |
| 首段文字关门、收到补充就作废在途回复 | 不选。会破坏已经开始的流式回答，也与 Datus 的执行边界不同。 |
| 照搬 Datus：任务内存队列，晚到输入启动新轮 | 不选。丢失收据或进程重启时难以确认提交状态，新轮也不符合同 Run 要求。 |
| **采用：PostgreSQL 持久收件，安全边界注入，当前 Run 续答** | 保留 Datus 的投递时机；V3 独有的部分是幂等收据和同 Run 收尾协议。 |

## HTTP、数据与状态

新增 `POST /api/sessions/{sessionId}/runs/{runId}/steers`：

```json
{"clientMessageId":"abcff107-e86e-4866-9236-fa2e2e976c61","message":"也给我北京时间"}
```

- 返回收据：`runId`、`clientMessageId`、原文 `message`、目标 Run 的 `runStatus`、可空 `messageSeq`。不返回独立的收据状态。首次持久化成功返回 `202`，此时 `messageSeq: null`；同 ID 同原文返回 `200` 和最新收据，即使该 Run 已结束。文本只用去空白后的结果判断是否为空，写入和幂等比较保留原文。
- 错误：非法 UUID 或空白文本 `400`；会话不存在、Run 不属于该会话 `404`；同 ID 不同原文 `409 ID_REUSED`；新 ID 在入口关闭后到达 `409 STEER_CLOSED`，原因 `LIMIT` 或 `TERMINAL`；超过新补充配额 `422 STEER_LIMIT`。先查归属，再查已有收据，最后检查入口和配额。不会将旧 Run 的提交改投当前 Run。
- 建议首版默认：单条至多 2 KiB UTF-8、每 Run 至多 8 条且累计至多 8 KiB，以先达到的限制为准。配额按所有已接受的新 ID 计，不因取件返还；幂等重试不消耗配额。配额不是模型容量保证，模型仍执行现有硬预算校验。

`agent_run_steer` 保存数据库生成的顺序 ID、`run_id`、`client_message_id`、原文、可空 `message_seq`、接收时间；唯一约束 `(run_id, client_message_id)`。取件用 `(run_id, id) WHERE message_seq IS NULL` 部分索引，且只消费仍在执行的目标 Run。收件顺序在目标 Run 行锁内分配。**不存 `state` 字段**；界面从 `messageSeq` 和 Run 状态推导：

| 判定 | 界面与含义 |
| --- | --- |
| 无 `messageSeq`，Run 仍为 `RUNNING` |「等待纳入」。服务端已收到原文，尚未写进聊天序列；即使入口已因 `LIMIT` 关闭，也以消息序号和 Run 状态为准。 |
| 有 `messageSeq`（不论 Run 状态） | 作为正式聊天气泡展示。它只表示原文已进入消息序列，不代表预检通过或模型已收到。 |
| 无 `messageSeq`，Run 已终止 |「未使用」。保留原文供手动复制，不自动重投。正常成功收尾不应留下这类记录。 |

在 `agent_run` 增加持久化关闭原因（运行中为空或 `LIMIT`，终态由现有 Run 状态派生）。新 Run 默认开放，对已存在 Run 的 schema 升级幂等，不改已有消息序号。已终态一律对外显示 `TERMINAL`，不继续显示耗尽预算的 `LIMIT`。已有 `agent_message` 仍由执行器单写入，不引入第二个消息序列。

## 执行与竞态

接收、取件、纯文本阶段收尾、失败收尾统一先锁目标 `agent_run` 行。事务内不做模型调用、工具执行或发布 SSE。继续采用单实例启动恢复；不通过 API 重启中断的执行器。

| 执行边界 | 规则 |
| --- | --- |
| 每次业务模型调用前 | 在同一事务按 FIFO 取当前全部尚无 `message_seq` 的记录，逐条追加 `user` 原文，并在同一事务回填其实际 seq。在准备第 8 次请求时，同一事务设置 `LIMIT`。提交是本次取件截止点。提交后更新内存视图并发纳入事件，再做压缩、容量检查和模型调用。之后到达的输入不影响本次请求。内部摘要调用不取件、不计入 8 次业务调用，仍用现有摘要预算。 |
| 模型返回工具调用 | 流式文字不改变入口。完整 assistant 工具调用和配套 tool 结果按现有顺序落库，不跳过已选定的工具，也不在这组消息中间插入补充。整批完成后回到请求边界。第 8 次仍返回工具调用时不执行新工具，按现有上限失败。 |
| 模型返回有效纯文本 | 执行器锁 Run，在事务内追加一次完整 assistant 消息，然后检查是否还有 `message_seq IS NULL` 的收件。**有待处理**：只提交这段回答，不关闭、不释放会话、不写检查点；发布非终态的回答提交事件，回到下一次取件。**没有待处理**：同一事务提交 SUCCEEDED、最终回答及有效上下文检查点并释放会话。无 delta 的适配器走同一条路径。 |
| 失败或启动恢复 | 只在同一事务结束 Run 和释放会话，不更新任何收件记录。因 Run 已终止，尚无 seq 的收件自动显示为「未使用」。已经纳入的消息、已提交回答和现有失败时的部分回答规则保留；不得重复追加已提交的文本，不推进跨轮检查点。 |

关门竞态以锁内事务为准：收件先提交，纯文本收尾就必须看到待件并继续；收尾先提交，后续新 ID 被拒绝并保留草稿。最后一次取件也是同样规则，先提交的补充进入第 8 次请求，后到的拒绝。允许前一段回答在第一个补充到来前已经发出所有 delta，只要终态事务还未提交，仍应续答。只消费由用户发起的补充，不自动空转。

## 对话视图与压缩

`ConversationContext` 从「首问 + 工具批次」改为按真实 `seq` 组织本轮：首问、每条补充、已提交的纯文本回答和完整工具批次。业务模型看到的示意：

```text
user          [本轮任务] 现在 UTC 几点？
assistant    UTC 02:00。
user          [本轮补充] 也给我北京时间。
assistant    tool_calls: convert_timezone (c2)
tool          tool_call_id=c2 → 北京时间 10:00
```

- 标签只由服务端按消息位置添加到出站视图，不存入原文。模型指令说明：后续补充按顺序调整本轮目标；仍适用的约束和结果需要保留；明确更正覆盖被更正内容。不能把用户文字里的同名标记当成元数据。历史轮中的真实 user 也按首问/补充映射，但不会变成本轮指令。
- 轻度压缩仍仅投影过大的工具结果，保留原 call ID 和回查地址。重度压缩保护**所有本轮真实用户消息**，只在用户消息之间折叠完整执行片段（批次或已提交的回答），摘要就地替换并标明来源 seq 范围。例如 `批次 A → 补充 → 批次 B` 不会折成 `补充 → A+B 摘要`。摘要和续跑提示只进入模型视图，不占用聊天消息 seq。
- 容量计算使用最终带标签的实际协议；如果不可压缩的用户原文、固定开销和回复预留已经超出硬预算，返回明确的容量失败，不截断用户文本。原文与收据仍可查看。失败轮仍不进入下一轮成功历史，也不通过模型原文回查自动复用。

## SSE、快照与浏览器

- 初始 SSE 保留现有一条连接。新增事件：`run.steer_gate`（至少用于 LIMIT，携带原因）、`run.steer_incorporated`（收据键、原文、真实 `messageSeq`）、`run.reply_committed`（非终态的完整段落及其 `messageSeq`）。现有 `run.completed` 只在最终事务成功后发一次。所有事件仍由 Run 执行器使用现有 `seq` 字段统一排号，只在对应数据库提交后发布。HTTP 收件线程不直接向 SSE 写入。
- 扩展现有会话快照的每个 Run：`canSteer`、`steerCloseReason`、`steers`，与消息、终态和活动 Run ID 在同一只读事务快照取出。首版保留现有全量快照和断线轮询，不新增历史分页或保证逐 delta 回放。
- 有可补充的活动 Run：输入按钮为「补充本轮」，流式文字不会关掉它。没有活动 Run：显示「发送」。还不知道 Run ID、LIMIT、切换会话时不能提交补充，输入框仍可编辑。保留当前 Run 的响应，切换会话后迟到的操作只影响旧会话，不覆盖新的输入框。
- 发送前冻结目标 Run ID、UUID 和本次文本。只清掉服务端确认接收的那段草稿，保留等待时新增的输入。网络结果未知显示「正在确认」，使用原 Run 和同一 UUID 查询快照或重试原 POST；未确认之前不允许把这段文本作为下一 Run 重发。首版可用标签页级 `sessionStorage` 保存这份**未确认提交**，确认或明确拒绝即删除，不保存其他草稿；切换会话时不得将这笔记录绑定到新会话。
- 渲染键：收据用 `(runId, clientMessageId)`，聊天消息用 `(runId, messageSeq)`。无 seq 的收件在收据区按 Run 状态显示；有 seq 时只由消息序列渲染一个用户气泡。合并时以已知非空 seq 和已知终态为准：迟到的 202 不得清除 seq，也不得用 `RUNNING` 覆盖终态；终态和 LIMIT 不能被迟到事件重新打开。活动快照合并已提交消息，兼容未落库的流式尾巴；终态快照替换临时内容。恢复原 SSE 断开后的页面状态时，不再次 POST 首问。

## 实现落点

- `SessionController` 增加收件 API；`SessionStore` 负责行锁、收件、消费、状态和快照事务。收件状态由 Run 与消息序号派生；数据库迁移与旧会话读取保持兼容。
- `AgentRunner` 统一控制取件、工具批次、纯文本阶段收尾与预算关门；`RunEvent` 保留现有序号协议，扩展事件载荷。用数据库返回的真实 seq 更新流式渲染身份，不在不同层分别推算。
- `ConversationContext` 维护本轮有序消息；`ConversationContextService` 只负责模型视图、压缩与容量。旧工具执行接口及原文回查地址无需改动。
- `chat-api.ts` 负责补充请求与重试；`chat.tsx` 负责输入模式、草稿和事件/快照合并。保留旧的普通发送入口。

## 验收与测试

| 场景 | 断言 |
| --- | --- |
| **已开始回答时再补充** | 收到第一个 delta 后提交，原段落不撤回，同一 Run/turn 依次持久化回答、补充、续答；续答真实出站带补充；只有一次 `run.completed`。 |
| 工具执行中连续补充 | 用可控工具屏障提交两条，整批只执行一次，出站顺序为完整工具批次 → 两条 user，原文 seq 可回查。 |
| 补充与纯文本收尾竞争 | 用事务屏障验证两种提交顺序：收件先则续答，终态先则拒绝，均不产生新 Run，且成功终态无未纳入收件。 |
| 第 8 次取件与补充竞争 | 先到者在最后请求中投递，后到者拒绝；纯文本仍可成功结束，工具回复按上限失败，不执行工具、不发第 9 次业务请求。 |
| 同时重试或跨窗口提交 | 同 ID 同文只产生一条收据和消息；不同原文冲突；错会话及旧 Run 的新请求不改变当前 Run；配额耗尽后仍可查已有同 ID 收据。 |
| 压缩与失败 | 强制「工具 A → 补充 → 工具 B」触发压缩，检查真实协议里的角色、顺序和工具配对；保护原文超预算时失败；已纳入原文仍在聊天中但下一轮模型看不到失败轮，不推进检查点。 |
| SSE 与 POST 回执同时丢失 | 用原 UUID 恢复；没有重复气泡、重复补充或第二次首问 POST。迟到事件不覆盖已知终态，旧会话回执不覆盖新会话草稿。 |
| 重启与普通提问 | 启动恢复只结束 Run，不更新收件表、不续跑；原先未纳入的收件派生显示为「未使用」，已纳入序号和已提交段落不变。无补充时的正常问答、工具事件和历史读取保持原行为。 |

后端用真实 PostgreSQL、可控模型流和事务屏障覆盖存储、执行器及 HTTP/SSE；前端覆盖草稿、按钮及快照/事件合并。首版限额一旦需要调整可独立配置，但不因此改变关闭顺序和幂等协议。
