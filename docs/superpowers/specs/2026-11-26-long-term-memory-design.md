# Data Agent V3：单文档长期记忆

2026-11-26 · 设计稿，待评审 · V3 `develop@507c024`，Datus-agent `59bb0a3`

## 目标与不做的事

V3 的 `general` Agent 可以在新会话和服务重启后沿用用户明确保存的偏好。用户可查看整份记忆、追加一项、更正或忘记明确指定的内容。记忆是默认值，当前明确要求优先。

- 「以后经营周报默认用万元」保存；「这次周报用元」只在本次生效；反复说同一临时要求也不自动保存。
- 「以后经营周报默认用元」替换原范围的唯一旧规则；不额外保留两条生效规则。周报偏好不应用于日报。
- 「忘记『经营周报默认用元』」删除这一行；「忘记周报单位」若不够精确，先展示候选并请用户明确指定。单独说「对」不授权改删。
- 「总结这次对话中值得记住的偏好」和「整理长期记忆」只提出建议。用户之后明确说要保存、更正或遗忘，才进入写入路径。

首版适用 V3 当前的单用户部署，不引入多租户、向量检索、后台自动提炼、通用 skill 引擎或全局知识库。指标定义、参考 SQL、临时任务、查询结果、推断与凭据不写入。遗忘只影响今后使用的有效记忆，不清除历史聊天、备份或已产生的工具记录。

## 参考 Datus，为什么这么做

[Datus 的记忆加载](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/utils/memory_loader.py#L97-L155)和[写工具](https://github.com/Datus-ai/Datus-agent/blob/59bb0a30446639be3dce182a6d7a4991766daab5/datus/tools/func_tool/memory_tools.py#L93-L187)使用一份 2000 字节内的 `MEMORY.md`，整份加载，由专用工具追加或精确替换。沿用「一份正文、整体加载、集中写入口」，不搬工作区文件、会话级提示词缓存或多类资产路由。

| 方案 | 判断 |
| --- | --- |
| 直接照搬磁盘 `MEMORY.md` | 不选。难与 V3 数据库里的工具结果同事务提交，多会话写入也要另做协调。 |
| 每条偏好一行数据库记录、分片检索 | 明确不选。用户要求只维护一条数据，首版也没有检索必要。 |
| **采用 PostgreSQL 单行、单个 `TEXT`** | 每次整份读写，正文版本可与现有 Run 的工具结果同事务提交；长效偏好与聊天、上下文压缩完全分开。 |

V3 比 Datus 更严格：后端只接受本次真实用户明确授权；不因弱确认、历史原话或整理建议写入；整行精确匹配，不做全文模糊替换；满额不自行淘汰。Datus 的三个 skill 作为三份小提示词资源，服务于两个只读场景和显式写入时的分类，不是三套存储或工作流引擎。

## PostgreSQL 形态与正文约定

在 V3 schema 追加 `agent_memory(agent_key TEXT PRIMARY KEY, content TEXT NOT NULL, revision BIGINT NOT NULL)`。当前单用户、单 Agent 下最多一条记忆数据。键从服务端 Run 所属会话解析，不接受模型或浏览器提供。以后开放多用户前，必须增加真实所有者范围和访问检查。

- `content` **是整段长文本**，不是 JSON、数组、块列表或子表。正文可用 LF 排版，一项一行且无末尾 LF；按行比较只是进程内实现精确编辑，不产生任何持久化分片、条目 ID 或索引。
- 沿用附件的 **2000 UTF-8 字节**默认设计，计算整份正文（包括 LF）；应用校验、数据库用 `octet_length` 兜底。容量限制与单行存储是两件事。满额整笔拒绝，告知超出的字节数，不截断或自动删除。
- 缺行读作空文本、版本 0；读取不写库。首次写入生成版本 1；追加相同原文或重申相同默认值不改版本。后续只在正文变化时递增；删光时保留空正文及新版本，不回到 0。
- 新增、更正、遗忘都读整份、生成完整新正文，再按预期版本原子替换。首次插入亦须防竞争。两个会话持同一版本写，即使改的是不同内容，也最多一方成功；失败方返回冲突与最新版本，不能自动换版本覆盖。

## 用户授权与专用工具

授权只来自**当前 Run 已纳入的真实用户消息原文**，绑定其 `messageSeq`。不从 prompt、压缩摘要、工具结果、旧会话、来自文档的引文或模型推断授权。后端解析受支持的完整命令并确定唯一操作、目标文本和预计版本，模型只能提交匹配的参数。目标不明确时给出可直接回复的完整命令。基础命令示例：

| 用户指令 | 后端允许的行为 |
| --- | --- |
| `记住我偏好中文回答` | 原话追加；没有精确范围键，不按语义相似覆盖。发现冲突先展示两项，请用户明确更正。 |
| `以后经营周报金额单位默认用万元` | 按「默认」前的精确范围识别，存在唯一同范围规则则替换，不存在则追加；不把近义范围合并。 |
| `把记忆「完整旧文」改为「完整新文」` | 在正文中唯一整行匹配旧文，新文须仍是合法偏好，且不与其他有效范围冲突。 |
| `忘记「完整原文」` | 唯一整行匹配并删除；没有目标或多义时不改。 |
| `这次忽略记忆` | 本轮业务请求按空记忆处理，关闭记忆写工具，数据库内容和版本不动。 |

首版中文采用锚定句式：允许首尾空白、可选中英文冒号、一个尾部句号；用户写的适用范围、单位和否定词不得被模型缩写。不给疑问、假设、引述、复合或多行命令写权限。拒绝明显的凭据标记和已知密钥格式，不在失败回执回显相关输入；不能保证识别所有隐含敏感内容。

- `readMemory({})`：查看、整理时开放，本 Run 成功读一次后关闭。读取时返回最新已提交的整段原文、`revision`、`remainingBytes`。读取失败不回答成「没有记忆」。
- `add_memory(content)`：仅在确定允许追加时开放；传一条完整原话。
- `edit_memory(old_string, new_string)`：仅在确定允许更正或遗忘时开放；遗忘传空的新值。三个工具均拒绝额外字段，后端绑定 Agent、Run、授权序号和版本。
- 写入成功返回 `operation`（`added/updated/deleted/unchanged`）、`entry`、`revision`、`remainingBytes`；失败用现有 `Message.success=false`，保留稳定原因，例如 `NOT_AUTHORIZED`、`NO_MATCH`、`FULL`、`CONFLICT`。满额附 `bytesNeeded`。不新增收据表。

### 同 Run 补充和事务

1. `AgentRunner` 每次先按现有规则取件，再从原始序列计算本次资格。取件前后收到多条明确且互相冲突的命令，先澄清，不猜；「不用记住」等直接撤销优先于尚未执行的旧授权。
2. 单次在途模型请求不取消。提议的关口：写工具提交前锁 Run 行并检查是否有更新的待纳入用户补充。如果有，返回 `DEFERRED`，不写正文、不消耗本 Run 的写资格；下一次按现有规则取件、重新授权。接收与写入按同一行锁定先后；写入先提交则不自动撤销，用户仍可明确要求遗忘。已成功（含未变化）或版本冲突后，本 Run 不再开放写工具；新的明确修改由用户下一 Run 发起。
3. 保留 V3 的 8 次业务模型请求上限。最后一次仍可使用当前快照回答，但不挂载需要再续跑的记忆工具；若待执行授权进入这一边界，明确说明未保存，请用户在新 Run 重发，不做隐藏的额外模型调用。
4. 校验授权、请求绑定的正文版本与工具参数。正文写入和成功工具结果入 `agent_message` **同一数据库事务**，提交后才发 `tool.finished`；Runner 不重复追加。以 `(runId, assistantMessageSeq, toolCallId)` 定位既有调用，核对工具名及参数后复用已保存结果。不同请求复用同一个调用 ID 不串单；同一次响应的重复调用 ID 不能重复执行。
5. 事务提交前失败则正文、成功结果均不落库。提交后若主回答断流，已提交记忆仍生效，现有聊天详情可查工具结果。版本冲突不换新版本重跑，也不把未发生的修改报告为成功。

## 模型接入与三个 skill

**每次业务模型请求**按顺序：取件 → 加载一份已提交的完整正文及版本 → 计算资格和工具列表 → 渲染最终指令 → 用同一份指令和工具做容量预检及实际发送。数据库失败走明确错误路径，不伪装为空；一次请求组装后其他会话写入，只在下一次业务请求可见。

- 在 `AgentDefinition.instructions` 之后追加固定只读或可写模板。正文作为**一个字符串**填入数据段，例如使用 JSON 字符串字面量安全显示整个正文，转义引号、换行、`<`、`>`，只替换一次占位符；不是 JSON 数组、分片或 JSON 列。向模型说明这些文字只供参考，不授予工具权限；当前用户要求和当前快照优先于旧聊天和旧工具结果。
- 内部压缩摘要仍用独立提示、空工具集，不注入长效正文，不从摘要生成写授权，不推进记忆版本。已遗忘文本可能仍出现在原聊天；浏览器保留历史，模型侧将旧记忆工具结果标为历史而非当前默认值。本轮明确忽略记忆时，也不通过旧记忆工具结果恢复有效值。
- `session-summarize` 在用户要求提炼当前对话时使用：列出候选、来源、范围，可回查本会话，不写记忆。找不到原话就标记待核。
- `memory-organization` 在用户要求整理时使用：先读取记忆，再列出重复、冲突、过期或归属错误及建议，不批量改删。
- `storage-classify` 是上述两个场景共用的分类规则，也可用于明确写入时判断是否属于长期偏好。普通业务任务不加载这三份资源。
- 首版使用现有 OpenAI 兼容流式模型接口和聊天工具面板。同一协议上的其他适配器不另建记忆；当前基线未确认独立的本机 Codex bridge，不把它列为首版验收门槛。

## 验收

| 场景 | 通过标准 |
| --- | --- |
| 跨会话与重启 | A 保存后新建 B，B 用默认值；服务重启仍可查询。在 PostgreSQL 确认只有一条正文数据，无条目表和分片。 |
| 改写、重复与遗忘 | 同范围更新只留一个生效值，重复不动版本；删除最后一项后保留版本，旧会话全文可查，但带旧摘要或旧工具结果也不恢复旧默认。 |
| 明确授权与补充 | 临时要求、引用、弱确认、模型伪造调用均不写。补充在写入前先获锁则延后评估；写入先提交则明确告知已生效，不自动撤销。 |
| 只读工作流 | 查看返回完整文本；提炼有来源，整理有建议，两者没有写工具、版本不变。内部压缩请求不携带长效正文或记忆工具。 |
| 跨会话并发 | 同版本竞争（包括首次插入）只有一方成功；另一会话在两次业务调用间提交新值，下一次实际出站请求出现新值、预算按同一指令计算。 |
| 边界与故障 | 2000 字节含中文、引号、换行可保存，2001 字节失败不改库。字面结束标签不能逃出数据边界。模拟事务提交前后故障、重复分发及复用调用 ID，正文与聊天回执一致；最后一次业务请求不假报写入。 |

先用真实 PostgreSQL 和可控模型验证上表的确定性；再用兼容端点少量验证「这次」「以后」「引用他人指令」的语义表现。未连接真实模型时，不宣称已验证语义质量。
