# Data Agent V3 首版通用 Agent 运行时设计

日期为 2026-11-26，设计已确认。

## 目标与范围

开发者可以为一个 Agent 指定系统指令和可用工具。用户可以连续提问，在页面上看到工具执行过程和回答。首版以时间查询和时区换算验证整个过程。以后接入新的只读工具时，开发者只需实现工具并将其加入 Agent 的允许列表。

已选定的范围包括 Agent 定义、单次执行与模型调用、工具契约与执行权限、会话与上下文、执行事件与前端输出。业务工具、写操作审批、多 Agent 调度、长期记忆和多模型路由留到有具体场景时设计。沿用 V3 的 Java 21、Spring MVC、MyBatis-Plus 和 React。业务数据保存在 Docker 上的 PostgreSQL 中。运行时独立于其他产品服务。

首版为单用户应用，所有会话均属于同一固定身份，业务表省略账号和租户字段。会话 ID 用于定位对话。工具允许列表按 Agent 生效。

## 方案选择

用户选择方案 A，由 V3 掌握执行循环。模型适配器只处理一次模型请求，工具授权、结果回填、轮数上限与事件顺序都由同一个 Runner 控制。代价是 V3 需要自行处理工具失败和模型终止条件。

备选方案 B 由 Java Agent 框架驱动循环。它能减少首个工具的接入代码，但 V3 的授权和消息记录依赖框架提供的拦截点。首版希望能够独立验证这些行为，因此采用方案 A。下述接口、上限及断线行为是本稿建议的默认值。

## 1. Agent 定义

首版在后端代码中注册一个标识为 `general` 的 Agent，包括系统指令、模型配置引用和允许调用的工具名。系统指令要求模型按需用工具，并在工具不可用时如实说明。工具注册表由本地实现构建，启动时检查重名以及 Agent 引用了不存在的工具这两类配置错误。

模型连接地址、模型名与凭据通过后端配置注入。首版建议对接一个支持流式文本和函数工具调用的 OpenAI Chat Completions 兼容端点。适配器只向 Runner 提供文本增量、单次响应结束原因、完整工具调用及错误。实现者可在现有 HTTP 客户端与兼容 SDK 之间选择，须关闭 SDK 自动执行工具的能力。

## 2. 单次执行与模型调用

一条用户消息启动一个 Run。一个 Run 归属一个 Session，可包含多次模型请求。Runner 按下列顺序推进。

1. 验证输入，原子占用会话，建立运行记录并写入本轮用户消息，然后发布 `run.started`。同一会话已有运行时拒绝新请求，返回 HTTP 409。
2. 组装上下文，将允许工具的参数描述一并传给模型。流式接收阶段可向页面推送回答文本。若模型分片返回工具参数，适配器按本次响应中的调用位置拼接，等待完整响应后才允许分派。
3. 若模型要求调用工具，先记录助手消息中的全部调用及各自的调用 ID，再按声明顺序逐个处理。每个调用都得到一个匹配该 ID 的成功或错误结果。整组结果写入后才发起下一次模型请求。
4. 若模型正常结束并给出最终回答，原子写入最终消息、将 Run 置为成功并释放会话，之后发送成功终态事件。模型响应截断、空回答、协议异常或连接失败结束本轮，记录失败原因。部分输出仍可供页面查看。
5. 每个 Run 最多发起 8 次模型请求。若最后一次响应还要求工具，直接以轮数超限结束，避免执行无法再用于作答的调用。模型请求设有限超时，失败后由用户发起新的一轮。

## 3. 工具契约与执行权限

每个工具声明唯一名称、面向模型的用途说明和参数 Schema，并实现接收已校验参数、返回结构化结果的方法。Runner 用同一份允许列表生成模型可见的工具清单，并在执行前再次检查名称。未开放的工具返回拒绝结果，参数错误返回可供模型纠正的错误结果，两种情况下工具实现均不会被调用。工具执行异常返回简短错误，模型可以继续作答，所有后续调用仍受轮数上限约束。

| 工具 | 输入与输出 | 验收边界 |
|---|---|---|
| `current_time` | 无参数，输出当前 UTC 时间，采用带 Z 的 ISO 8601 格式 | 从可替换的 Clock 读取，测试可固定时间 |
| `convert_timezone` | 接收带 UTC 偏移的时间和目标时区，输出同一瞬间的当地时间、偏移及目标时区名 | 使用 Java ZoneId 和时区规则；无偏移输入或未知时区返回参数错误 |

## 4. 会话与上下文

通过 MyBatis-Plus 将三类记录写入 PostgreSQL。以下为建议表名。

| 表 | 每行含义 | 保存内容 |
|---|---|---|
| `agent_session` | 一段对话 | 会话 ID、绑定的 Agent、当前运行 ID 和创建、更新时间 |
| `agent_run` | 一条用户消息触发的一次运行 | 会话 ID、轮次序号、运行 ID、状态、起止时间及失败原因 |
| `agent_message` | 一轮中一条完整的用户、助手或工具消息 | 所属运行、轮内顺序、角色和内容。助手发起的工具调用保存调用 ID、名称与参数，工具结果保存对应调用 ID、成功标志及返回值或错误 |

前端和模型均可从这些记录读取完整消息。SSE 文本分片保留在传输层。每次模型调用的输入按需从历史组装，前端专用状态和耗时不加入模型输入。

每次请求按顺序组装系统指令、最近成功的完整问答轮次、本轮消息。建议先取最近 10 个成功 Run，始终保留完整的工具调用与结果对。如果提供方报告上下文超限，将本轮标记失败并显示原因。失败 Run 可以在页面查看，其部分消息不参与后续追问。这样断在工具调用与结果之间的历史不会进入下一轮。

建议复用根仓库 Compose 的 `postgres` 服务与 `postgres-data` 命名卷，在同一 PostgreSQL 实例上使用 V3 专属的 `data_agent_v3` 数据库。当前 Compose 初始化覆盖的数据库尚未包含该库，实施时需支持在已有数据卷上幂等建库。V3 自己维护业务表结构，数据库连接参数通过后端配置注入。

后端按单实例运行。会话占用与释放在数据库事务中完成，保证两个浏览器标签并发发送时只有一个取得执行权。后端重启或 PostgreSQL 容器使用原数据卷重建后，已提交的会话历史仍可读取。若后端在执行中退出，下次启动接收请求前，在事务中将遗留的 `RUNNING` 运行标记为 `FAILED`，记录中断原因，并释放对应会话，用户可在原会话继续提问。

## 5. 执行事件与前端输出

沿用 React 页面和 Spring MVC。建议采用以下最小接口。

| 入口 | 行为 |
|---|---|
| `POST /api/sessions` | 创建绑定默认 Agent 的会话，返回 sessionId |
| `POST /api/sessions/{sessionId}/runs` | 提交一条消息并通过本次响应返回 SSE，前端使用 fetch 读取响应流 |
| `GET /api/sessions/{sessionId}` | 读取已记录的轮次、状态、消息和工具摘要，供刷新后重建会话 |

每条事件带 runId 和本轮内递增序号。事件依次反映运行开始、回答文本增量、工具开始、工具结束以及唯一的运行终态，名称分别为 `run.started`、`text.delta`、`tool.started`、`tool.finished`、`run.completed` 和 `run.failed`。工具事件带调用 ID 和名称。允许调用进入工具实现前发送开始事件，结束事件包含成功标志和结果摘要。被拒绝或参数无效的调用直接发送带原因的结束事件。页面按调用 ID 建立或更新工具条目。

页面把会话 ID 保存在 URL。发送后显示本轮输出和工具条目，结束后开放下一次输入。文本增量只追加到所属助手消息，遇到工具调用后，下一次模型输出从新的助手消息开始。收到最终消息时以完整文本核对展示，避免重复追加。失败时保留已有内容并显示原因。

浏览器断线后，已接收的运行继续到终态。Runner 的生命周期独立于 HTTP 输出，发送失败仅停止向该连接推送。刷新时通过会话接口读取快照，若运行仍在进行则短暂轮询至终态。无需持久化每个文本分片或重放 SSE。流式响应开始前使用 HTTP 错误码，开始后的执行错误通过终态事件表达。

## 验收

- 使用可控模型和固定 Clock 验证直接回答、同一 Run 连续使用两个工具、同次模型响应内的多个调用，以及基于上一轮具体时间追问。断言传给模型的历史、调用 ID 和时区换算结果。
- 构造模型请求未授权工具、参数错误和无休止调用的场景，分别验证工具未执行、模型可依据错误纠正、轮数超限只产生一次失败终态。
- 使用两个客户端同时向同一会话发送消息，验证仅一个 Run 被接受。模拟模型流中断，验证会话释放且下一轮上下文不包含失败轮的残缺调用。
- 在 Docker PostgreSQL 上验证三张业务表及并发占用。重启后端并用原数据卷重建数据库容器，验证已完成的对话和工具结果仍可读取。另行模拟后端在运行中退出，验证启动后中断轮次可查、会话可继续提问。
- 通过真实 HTTP 入口验证页面流式回答、工具状态、刷新后查看结果。同一轮断开浏览器再打开仍能找到原 Run。开发联调时再用配置的真实模型验证工具调用协议。
